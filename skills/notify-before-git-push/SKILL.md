# push 前后告知开 VPN；开 VPN 绝不能用注销弹窗

用户 2026-10-31 15:48 / 15:50 / 15:51 / 15:53 / 15:56 / 16:00 / 16:02 定，**所有对话、所有工程永久适用**（原话：「需要上传到我的 github 仓库时你跟我说一下！我开 VPN」「因为 GitHub 在国内访问、经常因为 DNS 污染不能直接访问！必须开 vpn 才行！」「不能访问我的仓库时给我说一声你来个通知或者弹窗让我知道这个！」「无论任何界面都要给我一个通知或者弹窗」「你判断能上我的仓库时就说明 VPN 应该是通的就不要给我弹窗了只给一个灵动岛通知也行」「让我开vpn的话必须给我弹窗、让我确定这个！」）。

## 铁律

**GitHub 在国内被 DNS 污染，不能直连，必须开 VPN。** 本机实测：github.com 普通 HTTPS 有时能通，但 Apelin 的 `git_push` 走另一条路径，不开 VPN 就反复报 `failed to connect` / `Operation timed out` / `SecureTransport OSStatus -9806`，开 VPN 后立刻恢复。**判断 VPN 通没通唯一可靠办法 = 直接试 push。**

## ⚠️ 血的教训（2026-10-31 16:06，别再犯）

**CountdownHUD 的请求文件前缀决定行为**：
- `!` = 纯文案（只显示、不动作）
- `?` = **注销确认弹窗**，按钮是「立即注销」，用户点 confirm 会**真 spawn sbreload 注销**！

**「请用户开 VPN」这种「不需要注销」的确认，绝不能用 `?` 前缀**（`?` = 注销弹窗）。我曾误用 `?` 弹窗做 VPN 确认，用户一点「确定」就触发了真的注销。正确做法见下。

## 做法（顺序固定）

1. **提交前**：本地改动先 `git_commit`（本地，不联网）。
2. **push 前告知开 VPN**（二选一，都**不触发注销**）：
   - **纯文案胶囊**：`sh scripts/hud-notify.sh 8 "!要推送 GitHub 了，请开 VPN"`（`!` 前缀，只显示）；
   - 或**对话里说清**「要推送了，请开 VPN，开好回我一声」。
   - **绝对不用 `?` 前缀的注销弹窗**。
3. **等用户回「开了/继续/推送」再 push**。
4. **push 成功 = VPN 通 = 只发一条纯文案胶囊「已推送」**，不弹窗、不发通知（2026-10-31 16:00 加）。
5. **push 失败**：正文说清 + 纯文案胶囊 `sh scripts/hud-notify.sh 8 "!push 失败，请开 VPN"`；不许静默失败、不许空转重试。等用户确认 VPN 就绪再重试。

## 弹窗/胶囊/注销的分工（务必分清）

| 需求 | 用什么 | 前缀 |
| --- | --- | --- |
| 只是知会（push 成功、任务完成、请开 VPN） | 纯文案胶囊 `hud-notify.sh` | `!` |
| 需要用户点「立即注销」的设备动作（注销/装包） | **注销确认弹窗** `respring-guard.sh --ask` | `?` |

**「请开 VPN」属于「知会」，不是「注销」，只能用 `!` 纯文案胶囊，不能用 `?`。**

## 边界

- `git_commit` 本地提交不受限。`git_push` 前告知开 VPN、成功后只发胶囊、失败才提醒。
- 其它联网操作超时，同样提示检查 VPN/DNS。

## 与其它技能的关系

- `notify-any-screen`：灵动岛胶囊跨任何界面；`apelin_notification_send` 只在 Apelin 退后台时显示。
- `respring-confirm-via-island-popup`：`?` 注销弹窗只用于「真要让用户决定注销/装包」的场景，与「请开 VPN」无关。
- `subagent-change-review`：子机器人改动提交前先核实，本技能是「核实通过、commit 之后、push 前后」那一步。
