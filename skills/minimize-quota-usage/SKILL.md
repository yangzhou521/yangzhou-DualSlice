# 额度最少优先（硬性规定）

用户 2026-10-31 21:10 原话：「以后所有的对话工作都以额度消耗最少为前提这个协助技能和记忆生成硬性规定并上传云端」。
**所有对话、所有工程、永久适用。**

2026-11-01 09:02 加严（用户原话「想办法减少额度消耗尤其是多条线」）：**多线/多机器人协作是额度黑洞，必须专门省。**

## 为什么这是硬前提

额度是真实约束，不是口号：

- WorkBuddy 的额度包一耗尽，整条子机器人线立刻停摆（`Credits exhausted …`）。
- 实测三个不同厂商（deepseek / minimax / glm）给出的重置时间完全相同，说明限制在**账号/网关层**，换模型线绕不过去。
- 一次 `apelin_conversation_read` 读长对话能拉回几万字，等于把额度一次烧掉一大截。
- **多条线互相回执/知会，每条都完整读上下文 + 生成回复 = 额度成倍烧。**

## 七条做法（照做）

### 1. 不为「顺手」主动排查
用户没要求时就不查设备状态、不读长日志、不反复确认。一次查询能答的不要查第二次。

### 2. 不主动派子机器人
每派一条就多一份完整上下文开销；额度一紧，子线先死。**要派先问用户**。

### 3. 不重复读长内容
- `apelin_conversation_read` 尽量带 `after_seq`（上次的 `last_seq`），不要整段重读。
- 技能 / 记忆 / AGENTS.md 用 `file_grep` 直接定位，别整份重读。

### 4. 一轮只做一件事
「改码 → 编译 → 装包 → 验证」压进**一个回合**。无依赖的工具调用放同一条消息一起发。

### 5. 回复要短
第一句给结论，只列改了/验了/没验的，不粘工具输出、不复述步骤。

### 6. 不做无关沉淀
只在真解决问题、或用户明确要求时写技能/记忆；同类合并进已有条目。

### 7. bug 只登记不修
登记到 AGENTS.md「已知 bug 登记簿」，要修先问用户。

## 多线协作的额外省法（2026-11-01 加，重点）

多线时最容易烧额度的就是「你一句回执、我一句回执、再对齐、再确认」。规矩：

1. **回执极简**：收到协作消息，只回一句「收到，照办」级别的回执，**不要复述对方整段内容**、不要把你自己的完整状态又列一遍。对方要的是「你收到了」，不是一份新报告。
2. **有结论才发**：没有新进展就不发消息。阶段性的「我在做/还差一步/等编译」这类纯过程，**别广播**；等有了「做完/失败/需要对方做什么」的实质结论再发。
3. **一条带全信息**：非发不可时，一条消息里把「做了什么 / 证据 / 需要对方做什么」三段一次写清，**别拆成一问一答来回传**。
4. **不频繁轮询**：不要 `apelin_conversation_read` 隔一会儿就刷一次看对方进度。等对方主动回，或只读最新几条（带 `after_seq`）。长等待（云编译、装机）就等，别空转去查。
5. **交接一次说清**：分工/合并这类协调，**一次把规则、文件边界、版本、下一步全说清**，对方一条「照办」回执就结束，不要多轮确认。
6. **能不问就不问**：能自己查的状态（诊断、CI、dpkg 版本）自己查完直接给结论，别把「你去看看」推给对方。

## 边界：正确性 > 额度

省额度**不能**省掉：

- 动设备前：正文写清原因与倒计时 + 灵动岛胶囊 + 弹窗让用户点头
- 装完注入 SpringBoard 的插件：查 `apelin_crash_list process=SpringBoard` 无新报告
- 要 push：先自己直接试 push，不通才请用户开 VPN
- 要用户拍板：立即主动弹窗（`respring-guard.sh --ask`），不能只等文字
- 汇报如实区分「已验证」与「未测试」

宁可多花一点额度把话说清楚，也不要省额度而让用户不知情、或把没验的说成验过了。
