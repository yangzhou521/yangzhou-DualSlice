# 跨对话协作：自己的活第一，协助只是辅助

**本机同时有多个对话在干活**（同一台 iPhone、同一批已装插件、同一套 GitHub 仓库）。前台只有一个、
设备只有一个、SpringBoard 只有一个，所以「谁在什么时候动什么」必须互相知道；但**每个人的本职是
把自己对话里用户交代的活干完**。

用户 2026-10-30 反复交代，**所有工程、所有对话、永久适用**（原话关键字）：

> 21:40「以上对话全部已经上传云端的内容这些同步改动现在同步给所有在工作的对话内」
> 22:22「有任务进展时…同步给所有 running 的对话内！…各个对话机器人智能地同步协调分配可关联的工作任务！并且
> 实时通报已经完全的任务、给下一个任务做准备工作！」
> 22:27「同步工作任务完成✅后要继续完成本轮对话的没完成的任务！」
> 22:33「别的对话任务是副加任务！自己对话内的任务要优化完成✅！…以自己任务为第一性原则！帮助别人只是辅助！
> 永远不要影响自己的任务！」

> 22:57「…在各自闲置时主动协助的别的机器人，并主动问它们要一些有什么需要帮忙的简单、容易、短时间能完成的小任务！」

这条技能把上面收成**一件事**：与别的对话保持同步，**但不拿协作当借口耽误本职工作**。配套、互不替代的
还有 `task-done-notify`（对**用户**的汇报 + 灵动岛胶囊）和 `respring-notify-countdown`（通知 + 5 秒倒计时 +
外出取证 60 秒回程）。

## 一、第一性原理：自己的任务优先（其余一切让路）

**优先级顺序，不许颠倒：**

1. **用户当前这条指令**（他刚说的话永远压过我的计划）
2. **本对话本轮自己没做完的任务**（用户交给本对话的活）
3. **协助别的对话 / 别的工程**（附加任务，只在第 2 项为空或真的阻塞时才做）

- **回执例外：别人的消息第一时间回，且不算耽误自己的活**（22:51 补条）。收到广播 / 协调 / 交接 / 提问，手上没有
  「一断开就会坏」的动作就**立刻回一句**（几秒）：先发回执，再读内容、再干活；正忙先给时限「收到，我在做 X，
  N 分钟内答复 / 让路」，做完补真答复。**沉默 ＝ 让大家一起空转，谁都不许因为等我而闲置。**
- 帮助别人是**辅助**，不是本职工作：**永远不要影响自己的任务**，也不要影响别人的任务。
- 「闲置」＝自己没有待办、没有等自己动手的下一步（单纯等云编译 / 等用户算半闲置）；**闲着就主动去问别人要
  「简单容易、几分钟能收尾」的小任务**（22:57 补条，做法见 §六），别干等、也别等别人开口；只做随时能停的活。
- 接了协助任务也要随时能被自己的任务打断：自己这边一来活，立刻广播一句「我回去做我自己的活了，
  你这个先停」。
- 同一批文件 / 同一台设备同一时刻只有一个对话在动；宁可排队，不要同时改。

## 二、找对话：两个调用 + 一条判据

```
apelin_project_list                                     # 全部工程（folder / projectID）
apelin_conversation_list                                # 本工程全部对话
apelin_conversation_list project: <folder|projectID>     # 逐个工程再列一次
```

判据（读每条的 `state` 与 `updatedAt`）：

| 状态 | 怎么办 |
| --- | --- |
| `running` / `waitingForApproval` | **在干活**，必须处理（协调 / 广播） |
| `open` 且最近几分钟有更新 | 当它刚结束一回合，也处理 |
| `idle` / `ended` | 不用管（发给 `ended` 只是白排队） |

**本对话自己排除**（`isThisConversation: true`）。要更确定就
`apelin_conversation_read`（带 `after_seq` 少读点）看它最后在做什么。

## 三、职责 A：风险动作前先协调（注销 / 装包 / 杀进程）

会打断别人的动作：`icli sb respring`、`apelin_device_respring`、
`apelin_package_confirm_loaded(respring: true)`、`sh scripts/respring-guard.sh …`、
`irisin-cli install`、`icli app kill <bid> --force`。

1. §二 的两个列表跑一遍。
2. 给每个「在干活」的对话 `apelin_conversation_send`：

   > 我是同一台设备上另一个对话（工程 X）。我准备在约 N 秒后注销 SpringBoard（原因：装了 Y）。
   > 请把当前这一步收尾：存进度、放下正在做的界面验证；离开 Apelin 的先自己回来。收尾完回我一句。

3. `apelin_conversation_read`（`wait_seconds: 60`）等它这一回合结束，多个就逐个等。
4. 超过约 120 秒仍没收尾 → **不硬注销**，回复正文写清「对话 A 还在做 X」，让用户决定。
   用户说「现在就注销、不用等」才照办，并在正文如实写。
5. 协调完才走「通知 → 正文写 5 秒 → 真等 5 秒 → 才执行」。
6. 汇报里写清查了哪些工程/对话、各自状态、发了什么、等了多久——「查了，没有别人在干活」也是要写的一句。

`apelin_conversation_send` 只是**排队**，不会打断它当前这一轮——这正是要的效果。
它是 `waitingForApproval` 时消息排在批准卡后面，这时把这件事写进回复正文告诉用户。

## 四、职责 B：进展与完成，实时广播给所有在跑的对话

**每有一件有结论的事，就广播一条**（不是每跑一条命令）：

- 做完一件事（修复 / 功能 / 检查，含真机验证结果与**没验的部分**）；
- 阶段进展：云编译出包、装包成功、诊断值变了、验证失败并找到原因；
- 要改设备状态了：装包、注销、杀进程、改第三方插件配置（如 Choicy 白名单）；
- 卡住了 / 在等用户（让别人知道别再等这条线）。

收件人：§二 里所有「在干活」的对话。格式**三行以内**，可照抄：

> [工程/对话名] 进展：<一句话做了什么>
> 证据：<跑了什么、看到什么值 / CI run 号 / deb 路径与大小>
> 下一步：<我接着做什么；需要谁让路或接手？>

分寸：

- 一件事一条；同类进展合并；**一个回合最多 2~3 条广播**，别刷屏。
- 广播给**对话**（agent 读），胶囊/通知给**用户**——两者都要，互不替代。
- 收件方读到后**第一时间回一句回执**（「收到，我在做 X，N 分钟内不动设备 / 让路」）：**别攒着**——发广播的人
  靠这句回执才敢往下动，不回就是让大家空等。

## 五、职责 C：动屏幕前后各同步一句

前台只有一个，谁都可能正在读界面树、点元素、截图（Apelin 自己还会抢前台）。所以要进桌面 / 进别的 App /
进设置面板之前，先广播一句：

> 我要去 <桌面 / Sileo / 设置> 取证，约 N 秒回来（60 秒硬上限），这段时间我占屏幕。

回来再一句：「回到 Apelin 了，看到 <结果>，外出 N 秒」。时间预算与回程脚本见
`respring-notify-countdown` 第三节（`scripts/errand-in-app.sh`，trap 保证回程）。

## 六、职责 D：闲置时协助别人（附加任务，有前置条件）

**顺序永远是：用户当前指令 > 本对话本轮未完成的活 > 协助别人。** 自己的活没做完，别去接别人的。

**分工原则——智能协调、合理分配**（用户 22:22「各个对话机器人智能地同步协调分配可关联的工作任务」）：几个对话
推同一个目标时，**先按能力 + 占用拆开再动手**——设备侧取证、云端查询（CI / Release / 注解）、源码实现、文档与
三样同步各归一方；**同一件事不许两方同时做**，改同一批文件必须排队（§九）；能拆成互不重叠的几块就当场分派：
**小任务给闲置的机器人，长活与要动设备（装包 / 注销 / 杀进程）仍归自己**；每有结论就广播，并把**下一步的活顺手
分出去**（谁空谁接），别攒在自己手里。

三条前置条件**同时**成立才动手协助：① 自己真的没有待办、没有等自己收尾的一步；② 手上没有随时会被
自己任务打断的界面操作；③ 对方确实需要并且说了「可以交给你做哪一块」。

自己手头空着、或只在等云编译 / 等用户时，**不要干等，主动去要「小任务」来干**（用户 2026-10-30 22:57 原话：
「比如 a b c d e f g 这些机器人在各自闲置时主动协助的别的机器人，并主动问它们要一些有什么需要帮忙的简单、
容易、短时间能完成的小任务！」）：

- 「小任务」的判据：**简单、容易、几分钟内能收尾、随时能停**（只读查询、查 CI/Release/注解、下载并校验、
  设备侧取证 / 读崩溃、写自己工程内的文档 / 技能 / 记忆、跑探针）。够不上「小」的（改别人源码、装包、注销、
  杀进程、要长时间盯的验证）当场说不接，或按 §七 走交接。
- **一次只要一两件**，做完**立刻回结果并再问一次还有没有**——既不让对方空等，也不让自己闲着。
- **索要 ≠ 代做**：对方没明确说「这块交给你」，就不动它的东西。
- 自己这边一来活，先说一句「我回去做自己的活了」再让位（§八）。

1. **主动索要**：给每个在干活的对话发一句（照抄可改）：

   > 我是同一台设备上的另一个对话（工程 `<folder>`），这边暂时空着（自己的活做完了 / 在等 X）。
   > 有没有**简单、容易、短时间能完成的小任务**给我？只读分析、设备取证、查 CI/Release、下载校验、
   > 写我工程内的文档/技能/记忆这类我立刻能做；改你工程源码、装包、注销、杀进程我不碰。
   > **一次给我一两件**，做完我回你结果，你这边一有变化我随时停。
2. **按能力分工**（这是能不能真正落地的关键）：

   | 能做 | 不能做 |
   | --- | --- |
   | 设备侧取证：`icli prefs read` 读诊断、`apelin_crash_*` 读崩溃、跑 probe、`icli log` | 改**别的工程**的源码/配置（`file_*` 工具出不了自己工程根） |
   | 查云端：GitHub API 读 run / Release / 注解（`icli probe` + `NSData` 或 `apelin_web_fetch`） | 替别人 `git_push`、发 issue、建仓库（要用户点头） |
   | 只读分析：二进制字符串、plist、dpkg 状态、镜像列表 | 用 shell 绕过工程边界去写别人的文件 |
   | 本工程内的实现、文档/技能/记忆的同步 | `apelin_conversation_stop` 别人的对话（实测被拒） |

3. **要动手改别人的东西，先接手交接**（见 §七）：对方明确说「这块交给你」，
   文件又确实在**自己能编辑的工程里**（本机所有插件源码都在 `yangzhou-DualSlice` 仓库里，
   **同一个仓库 ≠ 同一个工程**，先确认路径）才接手；接手后立刻广播「我接手了 <任务>，你停手」。
4. 帮完广播一条「我这边做完了 X，你继续」。
5. **自己的活一来，协助立刻让位**：先广播「我回去做自己的活了」，再去干；别把两边都拖住。

## 七、职责 E：交接协议与「替下一步备料」

交接必须可操作，三段式，缺一段就不算交接（模板照抄）：

> **任务**：<要达成什么，验收标准是什么>
> **现状与证据**：<改到哪一步、哪些文件/诊断键/CI run 号/包路径、验证过什么、没验什么>
> **下一步与命令**：<具体命令或代码位置、要不要装包/注销、要注意的坑>

收到交接的一方，**先回一句回执**（「收到，我接手，N 分钟内动手 / 我先不动」），**回执要在读到的那一刻发**
（不等读完细节、不等做完），再动手。

**完成一件任务时顺手备料**：把下一件事要用的东西留在广播（和工程文件）里——deb 路径与大小、
诊断键与期望值、CI run 号、脚本命令、已知坑。这样下一个对话（或下一个回合的自己）不必重新查一遍。
上下文被压缩是常态；交接到文件里比留在聊天里可靠。

## 八、职责 F：同步做完，立刻回到自己的活（不许拿协作当收工）

用户 2026-10-30 22:27 原话：「同步工作任务完成✅后要继续完成本轮对话的没完成的任务！」

- 广播、协调、协助、同步上云都是**插入动作**，不是本轮工作的终点。发完广播、协调完、帮完别人，
  **立刻回到自己本轮还没做完的活上继续干**。
- 做法：动手同步前先把自己本轮的未完项列一遍（写在回复正文里最好），同步做完照着这张单子往下走。
- 只有真的阻塞（等云编译 / 等用户 / 等对方回话）才转去做协助；阻塞一解除就回来。
- 一个回合结束前自问：**本轮的活都干完了吗？** 没干完就在正文写清「还剩什么、下一步是什么」，
  不许静默收工；也不许用「我去帮别人了」当理由不干自己的活。
- 接手别人的任务前，先把自己的未完项写下来（正文或工程文件），免得被上下文压缩掉。

## 九、红线（一条都不能破）

- **自己的任务第一**：不许因为协助别人而让自己的任务延期、漏做、或只做一半就收工。
- **不许静默**：收到广播 / 协调 / 交接 / 提问，必须**第一时间回一句回执**（先说回执，再干活）；
  让对方空等等于让整条线空转，也让别人误以为可以动设备。忙着就先回「收到，我在做 X，N 分钟后」。
- **绝不 `apelin_conversation_stop` 别人的对话**（实测：`an agent stops only the conversations it opened`）。
  只有自己开出来的对话才能停。
- **绝不改别人工程的文件**，也别用 `shell_run` 绕过去。
- **改第三方插件的配置前先广播**（例如 Choicy 的 `allowedTweaks` 白名单）：它影响别人正在做的验证。
- **「协助」不等于可以动设备**：装包 / 注销 / 杀进程仍旧走两道闸门（协调 → 通知 + 5 秒）。
- **别把广播当汇报**：用户读的是回复正文与胶囊，对话之间读的是广播。
- 崩溃循环 / 一进安全模式时优先救设备，但仍要在正文写清「我现在注销，别的对话会被打断」。

## 十二、非阻塞协作：把「等待」从协作里删掉（2026-10-30 23:40 起）

用户 23:40 原话：「机器人之间关联任务仍然效率低下 想办法优化解决一下」。病根就是**等待**：发消息等人回、
注销等逐个回执、依赖任务串行做。三条判据：**能查到的绝不去问，能并行的绝不串行，能只写不打扰的绝不发消息。**

**12.1 状态走共享黑板，不走消息**（用户 23:50：「为所有在活动的机器人建立一个统一的智能分配通知任务的技能，

判据：**信息只需要被看见 → 黑板；需要对方立刻改变行为（让路/停止/要结果）→ 才发消息。**

**12.2 先查状态，别发消息问**：`apelin_conversation_list` 的 `state`/`updatedAt` 与黑板的 `list`/`busy`

**12.3 注销用「定时公告 + 30 秒反对窗口」**，替代 §三 的「逐个发消息 + 等回执」：给每个 running /
waitingForApproval 对话发**一条**公告（不要求回执）——「约 30 秒后注销，只重启 SpringBoard，不杀你 App 内的

**只有真收到「等等」才顺延**（一次最多 60 秒），否则执行。依据：respring 只重启 SpringBoard，

## 十三、看护与接管：一两个机器人睡死，活也得有人接着干（2026-10-31 00:1x 起）

用户原话：「保持、保证一二个机器人睡死不工作的前提下还有别的机器人能同步接收它接下来的工作！
不至于任何机器都睡死过去！都不工作！智能的提高机器人之间共同协调解决用户任务的能力！」

**睡死 = 这段对话停在原地、不再更新黑板，也没在等用户**（对话 ended / idle 却忘了自己在干嘛 /
等审批里被闲置 / 上下文被压缩后丢了自己的任务）。**这是常态，不是意外**：机器人会停，任务不许停。

### 13.1 冗余最小单元 = 双人知事（接口必须离开聊天）

任何一件「还没做完、不能丢」的任务，**至少两方知道接口**：文件路径、诊断键与期望值、包名与版本、
Release 资产 URL、CI run 号、验收标准。写进**工程文件 + 黑板**（`post` 的「下一步」字段、
`add` 的验收字段、工程 `AGENTS.md` / README / 清单），**不许只留在某个对话的聊天里**——
那个人一睡，接口就跟着没了。别人凭黑板和工程文件就能接，这才叫冗余。

### 13.2 心跳与看护报告：一切自动，不额外发消息

```sh
F="$HOME/Documents/wiki.qaq.apelin/fleet/fleet.sh"
sh "$F" beat                      # 长活期间每几分钟一次：只刷新自己那行的时间，不动状态、不打扰别人
sh "$F" care [阈值分钟，默认20]    # 看护报告：谁睡死了 + 照抄就能执行的接管/唤醒指令
```

`start`（开工一条命令）打印的就是**看护报告**：收件箱 + 全队状态 + 谁睡死 + 谁空闲 + 设备占用 +
**全队活线数**（近 20 分钟更新过黑板的 agent）。活线 = 0 就是**全员停摆**，报告里会直接喊出来。
看护人不设专职：**谁在开工，谁顺手看一眼**，几秒钟的事。

### 13.3 接管：只接「随时能停、不冲突」的部分

```sh
sh "$F" takeover <你> <睡死那位的短id> "备注"    # 记账：我接着它的活，并把它那行标成 handoff
```

- **可以接**：只读查询、云端 CI / Release 查询、下载与校验、设备取证、写**自己**工程内的文档 / 技能 /
  记忆、三样同步、以及确认无人同改时在本工程里继续同一份源码。
- **不接**（除用户当次明确同意）：改**别人工程**的源码、装包、注销、杀进程、删包、动系统设置。
- 接管前先 `care` 看它是不是真睡、`list` 看有没有人已经接了；**一文件一写者**，黑板上 `handoff` 那行
  就是「别接着改」的标记。原 agent 回来时看黑板即可，不必等谁解释。
- 接管只解决「活没人干」；**等审批不算睡死** —— 见下条。

### 13.4 等用户点头（waiting-user）是唯一合法的停摆

`care` 会把它单独列出来。看护人做三件：① `apelin_notification_send` 提醒用户（Apelin 不在前台才可见）；
② `sh scripts/hud-notify.sh 8 "!等你点一下"` 让灵动岛胶囊在屏幕上也说一句；
③ 把这一件写进黑板 `waiting-user` 行，让别人一眼看出「不是没人干，是卡在用户这里」，而不是当睡死去接管。

### 13.5 三条防全体停摆的硬线

1. **不许把自己卡在「等对方回执」上**：等待期间必须并行做能做的部分，或 `want` + `start`（§十二）。
2. **设备类风险动作必须人人会做**：注销 / 装包 / 杀进程只走仓库里现成的 `scripts/respring-guard.sh`、
   `scripts/hud-notify.sh`、`scripts/errand-in-app.sh` —— 任何对话都能照做，**不依赖某个特定 agent 在世**。
3. **任何时刻至少留一条活线**：`care` 里活线 ≤1 且有人睡死时，看护人先接「随时能停」那部分，再去干
   自己的活；一件活做完必须在黑板写「下一步」，写不出下一步就 `want` 一条，别沉默。

### 13.6 落地位置

技能 `fleet-shared-board`（命令与红线）；黑板工具 `scripts/fleet.sh` v3（`beat` / `care` / `takeover`，
`start` 即看护报告）；`AGENTS.md`「硬规矩」；全局记忆一条。

## §十四 冲突即停对接（用户 2026-10-31 01:05 原话：「发现有别的机器人修改你要的内容时要立即停止工作和它对接！防止打乱你的安排的部署！对接完成后立即进行自己的任务！」）

发现有别的机器人正在修改你要改的内容（同一文件、同一工程同一份产出）时——**立即停止自己的修改，
先和它对接**，防止两手同改一份文件、互相覆盖、打乱部署：

1. **怎么发现冲突**：
   - 黑板 `plan` 的撞车检查标出「同一工程多人同时在动」；
   - 动手改文件前 `git_status` / `git_diff` 看到该文件已被改（且不是自己刚才改的）；
   - `list` 看到别人 post 了和你重叠的任务；
   - 自己被 `takeover` 标成 `handoff`——那就是别人认为你睡死了，把你的活接走了。
2. **立即停**：别继续改那个文件。再 `post` / `progress` 一行说明「停了，等对接」，把黑板自己的状态
   写清楚（别让别的机器人以为你还在动）。
3. **对接**：`apelin_conversation_send` 给对方一条消息——说清「我在改 X / 你在改 X / 谁让谁 / 划清边界
   （哪个文件归谁，或串行：谁先做谁后做）」。一次说清，别来回拉锯。
4. **对接完立即继续**：边界一定，立刻回到自己的任务接着做，别空等。对方让给你，你就接管；你让给对方，
   你去做自己另一件不冲突的活。
5. **红线不变**：一文件一写者；被标 `handoff` 的那个不要再动原文件，回来先看黑板。

这条和「一文件一写者」呼应，但强调**动态发现冲突时立即停、对接、再继续**，而不是闷头改导致互相覆盖。

## §十五 主仆分工与子任务派发（用户 2026-10-31 01:15 原话「当发现自己的主任务完成不了时及时的把子任务分配出去！让别人完成你的子任务！做到多个主仆机器人智能任务完美同步交接任务和进展！合理的分配资源！如果当前任务对话内执行处理和任务太困难！可以让本插件内的活动的主机器人自己开三四个子机器人！这个也要实现它」）

主任务太重、拆解后有独立可并行的子任务时——**主机器人主动把子任务派出去**，甚至**自己开子机器人**分担：

1. **何时派子任务**：主任务拆解后，某个子任务独立、不碰主机器人正在改的文件、有明确交付物 → 派出去（不用自己硬扛）。
   - 派给已有空闲方：`sh "$F" handout <能力> <工程> <任务> <验收>`；指定人 `assign <agent> <工程> <任务>`。
   - 对方 `claim` 认领、做完 `done` + 广播；主机器人 `apelin_conversation_read` 收结果验收。
2. **何时开子机器人**：当前对话任务太困难/太重（要同时推进多件独立的事、或一件超大任务拆成几片并行），主机器人用
   `apelin_conversation_create` 开 1~4 个子对话（子机器人），每个 prompt 写清：①子任务是什么 ②交付物与验收标准
   （文件路径/诊断键/包名版本/Release URL）③不要碰哪些文件（一文件一写者）④做完 `done` + 广播。**上限 3~4 个**，
   超过自己协调不过来。
3. **接口先钉死再并行**：派子任务前先定好交付物（路径、键名、期望值）、验收标准、截止——两边并行不互相等，
   子机器人做完广播结果，主机器人收口验收。备料写进工程文件别留在聊天里。
4. **主仆关系**：开子机器人 / 派子任务的是「主」，负责拆解、派发、验收、收口；子机器人负责执行单一子任务，
   做完即回报。主任务完成不了的部分拆给子，**不是整个甩出去**；主机器人始终留着核心部分自己做。
5. **交接与同步**：子机器人每完成一步 `progress` 刷新黑板；主机器人 `list`/`read` 收进展；子机器人卡住或 idle，
   主机器人 `takeover` 或重开。任务完成 → 子机器人 `done` → 主机器人验收 → 关子对话
   （`apelin_conversation_stop close:true`）。
6. **红线**：子机器人不碰主机器人正在改的文件（一文件一写者，见 §十四冲突即停对接）；不开超过能协调的数量；
   派出去的子任务必须是「随时能停、不冲突」的（只读/云端/文档/独立模块），改同一份源码的活不并行派。
