# 开机交付对账清单：先对账、后改码、攒一批一次推

用户 2026-11-05 23:15 / 23:27 定。**所有对话、所有工程永久适用。**

## 病根
以前是「注销 → 用户报一个 bug → 我改一个 → 推云编译 → 又报一个」。
一轮一轮：**烧时间、烧额度、bug 永远修不完**，而 `WORK-STATE.json` 的 buglog 一直没被当成主表。

用户原话：「以后装包进桌面要先对 bug 不要着急云端编译，注销后第一件事是对账单和 bug
和修复好的问题清单！我们都对齐好问题和项目全部解决好一次推送云端编译，要不一轮一轮
bug 修复不完也浪费时间和我的额度！」

## 固定循环（一步都不许跳）

### 第 1 步：注销回来，先对账，不改码
打开 `scripts/WORK-STATE.json` 的 `buglog`，加上用户这一轮报的所有问题，分类列给用户：

```
已修好的：B14 文件夹内外图标 ✅（0.0.8，用户确认）
          B17 图标阴影 ✅
待验证的：B18 控制中心图标 —— 需下拉控制中心目视
还没修的：B13 选择主题点不进、B15 日历无星期日期、B16 时钟不显示
新报的：  （这一轮没有）
```

**先把这张单子报给用户**，再动手。

### 第 2 步：一次只改一个变量，但攒成一批一次推
- 每一项单独改、单独静态自查（符号引用、版本三处一致、plist 结构）。
- **全部改完**才 push 一次。不要改一条推一次。
- 中间不推云编译，本地改坏了大不了重来，推一次就是一次成本。

### 第 3 步：buglog 是唯一权威，必须落盘
用户说「修好了」→ 当场把那条 `status` 改成 `已修（0.0.x，用户确认）`，`proof` 写清依据。
用户报新 bug → 当场加一条：

```json
{
  "id": "B19",
  "where": "桌面 ▸ 某个位置",
  "symptom": "现象（照用户原话）",
  "reported": "2026-11-05T23:30 用户原话「…」",
  "proof": "怎么证实/证伪",
  "status": "待修 | 待验证 | 已修（版本，用户确认）",
  "fix": "改了什么，或待定位的方向"
}
```

不许只回在对话里。对话会死、会被压缩、会换人；文件不会。

### 第 4 步：推送前做交付对账
把这一批 fix 与 buglog 逐条对照：
- 这批要解决的 = buglog 里 `status` 不是「已修」的全部，**一条都不能漏**
- 多改的（超出清单的）要说出来，问用户要不要
- 漏改的当场补，别等下一轮

## 为什么要写进文件
「记录 ≠ 执行」是被反复证明的病：待办写进文件就以为做完了。所以对账清单不只是记录，
它是**每一轮开工的第一个动作**——先读它，再动手。

## 配套
- 文件：`scripts/WORK-STATE.json`（机读，唯一权威）+ `scripts/WORK-STATE.md`（人读）
- 交接：`sh scripts/resume.sh` 会把 chain/step/pending 打出来
- 提交信息末尾写 `NEXT:` 行，`git log` 可考古
