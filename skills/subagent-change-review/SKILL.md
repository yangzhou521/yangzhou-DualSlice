# 子机器人的改动，提交上传前必须重新核实

用户 2026-10-31 15:46 定，**所有对话、所有工程永久适用**（原话：「以后子机器人的任何修改和修复你都要重新核实查一遍、再提交上传」）。

## 铁律

**子机器人（协作对话 / 并行线）报「改完了」之后，主对话（调度台）绝不能直接 commit+push。** 必须先亲自重新核实一遍它到底改了什么、改得对不对、有没有越界，核实通过才提交上传。

原因（本工作区实测的教训）：子机器人可能
- 记错时间点/状态，把「曾经坏过」说成「一直坏」；
- 碰了冻结文件、改了被占用的版本号；
- 砍模块时留下编译期符号引用，一 push CI 就红；
- 只口头说「没碰 X」，实际 diff 里动了 X。

## 核实清单（提交前逐项过）

1. **看 diff**：`git_diff` / `git_status` 看它实际改了哪些文件，而不是只听它说「改了 A 没碰 B」。对照它自己的汇报清单，多改一个文件都要问为什么。
2. **核文件归属**：一文件一写者。它改的文件是否在它被授权的范围内？有没有碰别人的文件、碰冻结清单（如角标、设置面板）。
3. **核版本号**：版本号六处（`TCP_VERSION`、build 脚本 `VERSION`、工作流 `env.VERSION` / `tag_name` / `name` / `deb-url`）是否一致、是否复用了已发布/已作废的版本号。
4. **静态检查符号引用**：`file_grep` 全源码搜它砍掉/改名的函数名，确认没有残留引用会导致链接失败（尤其砍模块时，别的文件还在调那个函数）。
5. **对冻结清单**：`scripts/version-lock.txt` 和 AGENTS.md 里用户点名的冻结项（角标、设置面板、0.9.24/0.9.26 等），diff 里一处都不能沾。
6. **编译清单自洽**：改了 build 脚本的 `TWEAK_SRCS` / `SHARED_SRCS` 后，确认被砍的 `.m` 不再被引用、保留的 `.m` 里没有「实现了但被砍」的悬空调用。

## 核实通过才提交

- 全部通过 → `git_commit` + `git_push`。
- 有疑点 → 打回给子机器人，让它说明或改；改完再核实一遍。
- **不要因为「子机器人说是对的」就跳过核实**；不要因为「改动小」就不看 diff。

## 与其它技能的关系

- `sync-on-arrival`：子机器人上线先对齐（报到→对账→回执），本技能是它**收尾侧**的配套——子机器人收工时，调度台复核。
- `verify-cloud-release`：CI 产物发布前重查 run 状态、用 compare API 核变更文件，同属「不轻信旧读数」。
- `tweak-skill-capture-standard`：复核中发现的坑/教训，沉淀成技能。
