# 推送云端编译前必须先问用户

用户 2026-11-06 02:42 定，**所有对话、所有工程永久适用**。
原话：「以后插件修复后上云端编译都和我确认 ✅ 不要自己推云端编译！」

## 铁律：不自己推

**改完代码的完整顺序**：
1. 改完 → 静态自查（符号引用、版本三处一致、plist 结构）
2. **报进展总结**（本次做了什么 / 遗留什么 / 下一步 / 怎么防复发）
3. **问用户「要推吗」**
4. 用户明确说「推 / 可以 / 去吧 / 好」→ 才 `git_commit` + `git_push`
5. push 成功后 30 秒一次盯编译

**以下都不算确认**：
- 用户没回复
- 用户回了别的话题
- 用户只说了「继续」以外的指令（要具体判断，说的是别的任务就不算）
- 之前的某次确认（一次确认只覆盖一次推送）

**即使你觉得改动很小、很确定、很紧急，也不许自己推。**

## 为什么要问

云编译一次几分钟：推错要等、要回滚、要重编，浪费的是用户的时间和额度。
用户还会发现「同一批里夹带了别的改动」这类问题——推之前让他看一眼最省事。

## push 本身的做法（确认之后）

1. **先自己直接试 push**，通了就直接干、只发胶囊「已推送」
2. **第一次失败就立即弹** `sh scripts/vpn-guard.sh 20 "push 失败（连不上 GitHub），请开 VPN"`，不许重试、不许探测、不许只发胶囊
3. 用户点「确认开」后才重试、只试一次
4. 绝不在 push 前就让用户先开 VPN

## 盯编译

push 完立刻 30 秒一次查 `icli probe scripts/ci-status.js`，看到 `completed` 才停，一轮最多 10 次。
success 立刻下载 deb + 弹窗（装包还要再问一次）。
